# Crephore Web: Agent Instructions

This file is the source of truth for this repository's structure, API, auth, form, and testing conventions.
Follow it for every change, and update it when conventions change.

The structure mirrors the Zao POS web app (`~/Projects/zao/zao-pos-web`). When something is not covered here, follow how that project does it.
Intentional differences from zao: SSR for public pages (zao is `ssr: false`), the `landing` layout and `site-theme/` for the public site and event websites, `config/navigation.ts` instead of inline sidebar data, and the `c-`/`C` prefix instead of `z-`/`Z`.
The API is `../crephore-backend` (see its `CLAUDE.md`); keep types in sync with its DTOs.

---

## Tech Stack
- Nuxt 4 (`app/` directory), Vue 3, TypeScript
- UI: shadcn-vue (`app/components/ui`, no prefix, auto-imported), Tailwind CSS 4, `@lucide/vue` icons
- State: Pinia (`@pinia/nuxt`)
- HTTP: axios through `app/lib/axios.ts`
- Forms: vee-validate + zod (`@vee-validate/zod`, zod 3 syntax: `z.string().email()`)
- Toasts: vue-sonner through `cToast()` in `app/lib/cToast.ts`
- Drag to reorder: `vue-draggable-plus` (SortableJS). For vee-validate field arrays pass `customUpdate`: put Sortable's DOM move back and call `useFieldArray().move(oldIndex, newIndex)`. The editor's lists (`WebsiteSectionList.vue`, `WebsiteListField.vue`) reorder plain arrays the same way.
- Tests: vitest + `@nuxt/test-utils` (`environment: 'nuxt'`)
- Package manager: pnpm (version pinned in `package.json` `packageManager`; dependency build scripts allowed in `pnpm-workspace.yaml` `allowBuilds`, as in zao). Do not use npm or commit a `package-lock.json`.

## Project Structure
- `app/features/<feature>/`: the data side of one feature
  - `<feature>.type.ts`: request/response types mirroring the backend DTOs
  - `<feature>.api.ts`: one function per endpoint plus a `<Feature>ApiRoutes` object; only uses `get/post/put/patch/del` from `~/lib/axios`
  - `<feature>.store.ts`: Pinia setup store (`use<Feature>Store`), when state is shared across pages
- `app/pages/`: routes
  - Route groups: `(auth)/` (`sign-in`, `sign-up`, `auth` layout) and `(dashboard)/` (signed-in `dashboard/**` and `admin/**`, default layout; set `area` in `definePageMeta`). `index.vue` is the public landing page (`landing` layout).
  - A page is `<route>/index.vue`; its page-only pieces live next to it in `_components/`: `<Name>Form.vue`, `<Name>FormFields.vue` (reusable field groups), and `<name>.form.schema.ts` (zod schema, `<name>FormInitialValues`, `mapFormValuesTo<Request>()`).
  - `_`-prefixed folders and `.ts` files under `pages/` are not routes (`pages:extend` hook in `nuxt.config.ts`).
- `app/components/`: app shell as in zao (`AppSidebar.vue` with `NavMain.vue` / `NavUser.vue`, `SiteHeader.vue` (the breadcrumbs; sticky, `h-16`, so anything else sticky on a page starts at `top-16` or below), `ModeToggle.vue`, `AppLogo.vue`, `AppLogoMark.vue`, `PagePlaceholder.vue`, `landing/*`; subfolder names prefix the component name, e.g. `LandingFeatureCard`)
  - `custom/c-<name>/C<Name>.vue`: reusable building blocks, registered without a path prefix (zao's `custom/z-*/Z*`)
    - `c-form/`: `CFormTextField` (`#description` slot; `type="password"` renders `CPasswordInput`; `#addon-start` / `#addon-end` inside the input), `CFormSelectField` (`clearable` sends `null`), `CFormTextareaField`, `CFormCheckboxListField`, `CFormDateField` (date only, `"1948-02-14"`), `CFormDateTimeField` (a wall-clock string `"2027-06-12T15:00"` sent with the event's `timezone`; the API converts it to UTC). Use `CFormDateTimeField` for every date/time field, never `<input type="datetime-local">`.
    - Help text: every `CForm*Field` takes a `#field-info` slot (a popover behind an info icon by the label). Use it to explain what a field is for; use `#description` only for a short hint that should always be visible.
    - `CPageHeader`, `CPillTabs` (use inside `<Tabs>` in place of `TabsList` for a page's main tabs), `CToast` (mounted once in `app.vue`), `CConfirmationModal` (confirm destructive actions outside the table dialog), `CDateTime` (see `date.ts`).
    - `c-alert/CAlert.vue`: `type` (`info`, `warning`, `error`, `success`) picks `toastAndAlertStyles[type]`; `description` is HTML, only Crephore's own text. Use it for every alert, never the bare shadcn `Alert`.
    - `c-data-table/`: paged tables ported from zao (`CDataTable`, `CDataTableCard`, column defs, `CDataTableFormDialog`), with server-side paging, sorting and search. Row actions are labelled buttons ("Edit", "Delete"), never a "⋯" menu (unlike zao); `updateItemLabel` renames the edit button; `onAddItemClicked` / `onUpdateItemClicked` add or edit elsewhere; exposes `reload()`.
  - `ui/`: shadcn-vue components. Add them with `pnpm dlx shadcn-vue@latest add <name>` and do not edit them by hand. They style state with `data-open:`, `data-checked:` … while reka-ui sets `data-state` / `data-orientation`; `assets/css/tailwind.css` maps those with `@custom-variant`, so keep that list in sync when a new component uses another state variant.
  - Import app and custom components explicitly in `<script setup>` (as zao does); `ui/` components are auto-imported.
- `app/lib/`: `axios.ts` (request helpers, error toasts, refresh-and-retry, `isAuthFailure`, `getApiErrors`), `cToast.ts`, `table.ts` (`valueUpdater`), `form.ts` (`applyServerErrors(form, errors)`), `app-bootstrap.ts` (`init()` loads signed-in data), `date.ts` (`formatDateTime`, `formatDateTimeRange`, `formatTimeZone`, `isOtherTimeZone`, `browserTimeZone()`, `timeZoneOptions()`)
  - Event times are always shown in the event's `timezone`, never converted to the viewer's. Render them with `CDateTime`, which adds a muted "(Manila, GMT+8)" only when the viewer's UTC offset differs; use the same muted "(City, GMT+8)" wherever a timezone is named. Dashboard pages pass `browserTimeZone()`; server-rendered pages (the event website) pass `null` until mounted so server and browser render the same.
- `app/utils/styles/`: shared style maps (e.g. `toast-and-alert.ts`)
- `app/plugins/api.ts`: the axios instance (`$api`), `baseURL` from `runtimeConfig.public.apiUrl`, `withCredentials: true`
- `app/composables/`: `useBreadcrumbTitle(title)` (names the last breadcrumb on routes ending in an id), `useSiteAddress()` (event website addresses: `domain`, `hostOf`, `urlOf`; never hard-code `crephore.com`)
- `app/middleware/auth.global.ts`: route guard
- `app/types/api.ts`: `ApiResponse<T>`, `ApiPaginatedRequest` (`page`, `pageSize`, `sort: ['field:asc']`, `searchKey`), `ApiPaginatedResponse<T>`
- `app/config/`: `navigation.ts` (drives the sidebar, breadcrumbs and admin overview), `brand.ts`
- `app/components/sections/`: event-website sections (see "Sections")
- `app/components/site-graphics/dividers/`: `site-dividers.ts`, a catalogue of small line drawings by kind of event, drawn by key with `SiteDivider.vue` in `currentColor` (a colour class and a 5:1 size, e.g. `h-5 w-25`). Keys are stored on saved sections, so never rename one.
- `app/components/site-editor/`: controls shared by the website editor and the admin playground: `ThemeControls.vue` (Colors, Fonts & corners, Animation via `MotionControls.vue`; emits `play-intro`), `ColorInput.vue`, `PreviewFrame.vue` (desktop / tablet / phone)
- `app/site-theme/`: theming for the event websites hosts build
  - Font pairings (`fontPairings.ts`): the picker groups them by how the heading looks, in plain words (`fontPairingGroups`: Classic & Elegant, Handwritten (every cursive heading), Clean & Simple, Big & Bold, Fun & Friendly); groups aren't saved, so a pairing can move. Keys are stored on saved websites, so never rename one, and add new keys to the API's `WebsiteKeys.FontPairings`. Every family is a Google Font by its exact name, or a Fontshare one when its `SiteFont` sets `provider: 'fontshare'` (e.g. `modern_editorial`'s Boska and Switzer, and the 58 `fs_…` pairings, Fontshare's own pairs named after their fonts; a family Google also has comes from Google, so it has one source); `siteFontFamilies` passes the provider to `@nuxt/fonts`, which serves both from the app. Every family's `@font-face` rules are in every page, so keep to the weights already used (headings 400 plus italic, bodies 400/500/600) and the Latin subset (`fonts.defaults.subsets`). Restart the dev server after adding a font.
  - Heading sizes (`SiteTheme.heroHeadingSize`, `headingSize`: `headingSizes` small / medium (default) / large / extra-large, saved like the corner style and checked against the API's `WebsiteKeys.HeadingSizes`; set in Style › Fonts & corners): `--site-hero-heading-scale` and `--site-heading-scale` (`HEADING_SCALE`) scale the text-size steps (`--text-xl` … `--text-9xl`) on the hero's `h1` and on every other section's `h2` (and the program's venues heading) through a base rule in `tailwind.css`, so layouts keep their own sizes and phone-to-desktop steps; give a section's main heading `h2` so it follows.
  - Headings are set in their pairing's weight (`SiteFont.weight`, 400 unless set, e.g. a Fontshare pair's Medium, `modern_editorial`'s Boska Light): `--site-font-heading-weight`, applied to heading-font text by a base rule in `tailwind.css` (a weight utility on the element still wins); sections never bold them. A `script` heading is never slanted nor set in capitals: write italic heading text with `[font-style:var(--site-font-heading-italic)]`, never `italic`, and heading-font capitals with `[text-transform:var(--site-font-heading-case)]`, never `uppercase` (`test/nuxt/sections/heading-case.test.ts`).
  - `SiteTheme` colours: `primaryColor` (required), optional `secondaryColor` (unset, `secondaryFor` derives one), optional `accentColor` (buttons and small highlights, kept at 3:1 per background as `--site-accent-<background>`; unset, the other brand colour is used; never for text), optional light `backgroundColor` (`lightBackground` keeps oklch lightness ≥ 0.92; unset = white). Text and button colours are checked against the chosen background, not white. Unset optional colours are left out of the theme (null to and from the API).
  - Colour presets (`presets.ts`): six per kind of event (`eventKinds.ts`: `eventKindFor(eventType)`, `eventKindLabels` everywhere kinds are shown); a new website starts with `defaultColorPreset`. Names are only labels (colours are saved, not presets), and every preset must pass `siteThemeWarnings` (tested).
  - Contrast (`color.ts`): text on a colour (`readableTextOn`) is white whenever white reaches `PREFER_WHITE_FROM` (2.2, deliberately below WCAG AA), else whichever of white and near-black contrasts more. Brand colours used as text, buttons and highlights go through `ensureContrast`: kept as picked at `MIN_CONTRAST` (3, deliberately WCAG's large-text floor, for all site text), else shifted in lightness only, whichever way is the smaller change. Buttons and highlights reach 3:1 against their background or are clearly a different colour (`MIN_BUTTON_DISTANCE`); a button's text is always checked against the button.
- `app/features/site-motion/`: `SiteTheme.motion` (`intro`, `intensity`). Only the intro animates: sections, text and photos never animate on scroll (tried and removed). Keys are stored on saved websites and listed in the API's `WebsiteKeys`, so never rename one; when replacing or removing an intro, map its key in `normalizeSiteMotion` (`site-motion.type.ts`, used by `websiteFromApi` and `EventSitePage`; unknown keys become defaults). `motionForEventType` picks a new website's intro; `presets.ts` has lengths, `intensityScale`, `motionVars` (`--motion-intro-duration`) and `REDUCED_INTRO_MS`.
  - Scenes (`PageIntroScene.vue`, `scenes/<kind>.ts`, loaded on demand by `loadScene`): every intro is a scene; `scenes/index.ts` has each scene's server-rendered first frame (`sceneCovers`) so the page never flashes. Authoring rules:
    - Build DOM from HTML strings in the intro's layer and animate through the kit (`scene.kit.ts`): every duration goes through `A`, `wait` and `tween` (scaled by intensity, stopped on skip), never `setTimeout` / `setInterval` / `requestAnimationFrame`. SVG ids come from `uid`. Call `reveal()` once (except `vellum`); await `confetti(…)` before ending. Canvas scenes draw in `tween` at most at twice the pixel density and remove their canvas; endless loops use the file's `loop` helper.
    - Colours only through the variables `.intro-scene` sets (`assets/css/site-motion.css`: `--p`, `--a`, `--txt`, `--on`, `--hero-bg`, …); natural materials (paper, flame, night sky) may stay literal. Fonts through `--f-display` / `--f-script` / `--f-body`.
    - Text comes from `IntroContent` (`introContentFor(sections, occasion, kind)` in `intro-content.ts`; dates month first). Host text always goes into HTML through `esc`, and a scene leaves out what's missing. Sample text suits the event's kind and is never mixed with real program items.
    - `test/nuxt/site-motion/scenes.test.ts` plays every scene with hostile host text and with only a title.
  - The overlay (`.motion-intro`) is server-rendered with the first frame and ends on its CSS timer without script. A tap or key skips it. Only the event's website locks scrolling while it plays (`scroll-lock.ts`). With `prefers-reduced-motion` it's a 200 ms fade.
- `app/layouts/`: `default` (signed-in sidebar shell, calls `init()` on mount), `auth`, `landing`
- `app/assets/css/`: `tailwind.css` (entry) imports `tailwind-tweakcn.css` (theme tokens from tweakcn; edit with the tweakcn editor and paste back)

## Event Websites (guests)
Guests open an event's website at `<subdomain>.<site domain>`: `ana-and-marco.crephore.com`, or `ana-and-marco.localhost:3000` in development (Chrome, Edge and Firefox send `*.localhost` to this machine; Safari may not).
1. The site domain comes from `runtimeConfig.public.siteBaseUrl` (`NUXT_PUBLIC_SITE_BASE_URL`, default `http://localhost:3000`); `features/sites/site.ts` (`siteAddress`, `siteSubdomainOf`) and `useSiteAddress()` build and read addresses from it.
2. Routing by host (`app/router.options.ts`): on an event's subdomain the app has one route, `/`, rendering `pages/_site/EventSitePage.vue` without a layout (any other path redirects to `/`); on the site domain itself (and `www`) it is Crephore with the pages in `pages/`. It runs per request on the server and once in the browser.
3. `EventSitePage` loads the published website (`features/sites/site.api.ts`, `getSite` → `GET /sites/{subdomain}`, no sign-in) with `useAsyncData`, so it is server-rendered and the browser never calls the API. It renders the sections with `SiteThemeScope` + `SectionRenderer` (`priority` on the first), titled with the event's name, and skips section types the app no longer has; unpublished and unknown addresses get a 404 "This website isn't available" page.
4. `/` is server-rendered, not prerendered: one prerendered page would answer for every event's address.
5. The API client never toasts on the server, nor for `/sites/…` requests (`SILENT_URL_PREFIXES`).

## API Conventions
1. Every endpoint returns `ApiResponse<T>` (`{ success, data, message, errors }`); type API functions as `post<ApiResponse<T>>(...)`.
2. Never call axios directly from pages or components; add a function to `features/<feature>/<feature>.api.ts`.
3. The API client already shows the API's `message` as an error toast (except for `SILENT_URLS`), so callers should not toast errors again. Use `applyServerErrors(form, getApiErrors(error))` to also show field errors inline.
4. The API URL comes from `NUXT_PUBLIC_API_URL` (`.env`, see `.env.example`); never hard-code it.

## Auth
1. Auth is cookie-based. Login sets HttpOnly `accessToken` (30 minutes) and `refreshToken` (7 days) cookies that JavaScript cannot read; requests send them via `withCredentials`.
2. `useAuthStore` keeps `user` in memory plus an `isAuthenticated` flag in localStorage. The flag only drives route guarding; the API stays the authority.
3. Login (and sign-up, which logs in right after) calls `authStore.setAuth({ user })` from the login response.
4. The default (sidebar) layout calls `init()` on mount, which loads `GET /auth/me` and restores the user after a refresh.
5. Logout: `authStore.logout()` calls the API and always clears the local session, even if the API call fails.
6. Refresh, as in zao-pos-web (`lib/axios.ts`): a 401 (except from login, refresh and logout) calls `POST /auth/refresh` once and retries the request. Requests failing at the same time share one refresh (each refresh rotates the token). If the refresh fails, or the retry gets a 401 again, the session is cleared and the user is sent to `/sign-in?reason=session-expired`. Covered by `test/nuxt/auth/axios.refresh.test.ts`.
7. `auth.global.ts` sends signed-out visitors away from `protectedPaths` (`/dashboard`, `/admin`) and signed-in users away from `/sign-in` and `/sign-up`. It only runs on the client because the flag lives in localStorage. Add new signed-in areas to `protectedPaths`.

## List Pages
1. Lists use `CDataTable` inside `CDataTableCard`, like zao: a `<Feature>Table.vue` builds `tableProps` (`resourceName`, `columns`, `loadItems`, `addItem` / `updateItem` / `deleteItem`, `form` + `formInitialValues` + `formFieldComponent`, `mapItemToFormValues`).
2. Page-local files next to the table in `_components/`: `<name>.table.columns.ts`, `<name>.form.schema.ts`, `<Name>FormFields.vue`, and expanded-row panels when needed.
3. One table per page. Data that organises a list sits beside it as a side panel that filters it, not on its own page or in `Tabs`: e.g. My events has `EventGroupsPanel` (closed by default, open state remembered per browser; the selected filter shows as a chip above the table). Events are only grouped there: the event form has no group field, a new event goes into the selected group, and saving an event's details never changes its group. Lists that stand on their own become separate routes, as sidebar sub-items (`children` in `config/navigation.ts`) if they belong together.
4. Records with more than one form's worth of settings get their own page instead of the edit dialog (e.g. `/dashboard/events/[id]`). The table's "Manage" button (`onUpdateItemClicked` + `updateItemLabel`) and the name column link there; adding stays a quick dialog that then opens the new record's page, and deleting stays in the table.
   - The page loads the record by id (skeleton while loading, "not found" empty state), names the breadcrumb with `useBreadcrumbTitle`, and splits its parts into `CPillTabs`. An event's tabs: Details (`[id]/_components/EventDetailsForm.vue`; a memorial also has optional `bornOn` / `diedOn`, sent as null for other types), Venues, Program, Website and Guests & RSVP (placeholder).
   - The active tab is in the URL (`?tab=website`; none for the first tab). Tabs with unsaved edits are `force-mount`ed and hidden when inactive, so edits survive switching tabs.
   - Saving: a save bar above the form (`EventSaveBar.vue`) with "Save changes" / "Discard changes" (disabled until something changes), the error alert style with "You have unsaved changes." while there are any, success with "All changes saved." otherwise. Discard resets to the saved record. Leaving with unsaved changes asks first (`onBeforeRouteLeave` + `CConfirmationModal`, and `beforeunload`). The Venues, Program and Website tabs work the same way.
   - An event's end is optional (`endsAt` null): its page shows just the start, and the Program tab's days run from its day to the day after.
5. When one part of the page changes data another shows, reload it: re-create the table with a `:key` (the filter plus a version bumped on changes, so it starts on page 1); panels and `CDataTable` expose `reload()`.
6. TanStack Table is pinned to v8 to match zao; do not upgrade to v9 without porting `c-data-table`.

## Forms
1. Use `useForm({ validationSchema: toTypedSchema(schema), initialValues })` and `CFormTextField` for inputs. Add new field types as `custom/c-form/CForm<Type>Field.vue`, following zao's `ZForm*Field` components.
2. Keep client validation in sync with the backend request DTO (lengths, required fields, password rules).
3. Return one error per field: use `.pipe(...)` for format checks that should only run after a "required" check.
4. Trim text in the `mapFormValuesTo<Request>()` mapper, never the password.
5. Disable the submit button while `isSubmitting` and change its label (e.g. "Signing in…").

## Sections
Sections are the building blocks of the event websites (Hero, RSVP, FAQ, …). They render in the admin playground, previews, the host editor and the public event site, so they follow strict rules.

1. Where things live:
   - `app/features/sections/<type>/` (`hero`, `countdown`, `message`, `about`, `people`, `program`), matching `app/components/sections/<type>/`: `<type>.type.ts` (content interface and `<type>Fields`), `<type>.registry.ts` (the type and its layouts), `<type>.options.ts` (its layout options), `<type>.helpers.ts` when it has logic.
   - `app/features/sections/` files apply to every type: `section.type.ts` (`Section`, `SectionContentMap`, `SectionLayoutProps<T>`, `SectionOccasion`, `sampleOccasion()`, `OccasionTime`, `inPickerOrder`, `sectionBackgroundLabels`), `section.cta.type.ts`, `section.background.ts` (`backgroundStyles`, `resolveBackground`), `section.fields.ts`, `section.options.ts` (shared choice sets, `resolveLayoutOptions`, `positionClasses`, `alignClasses`, `overlayFor`, `groupedChoices`), `section.layout-options.ts`, `section.layout.ts` (`layout()` and the shared background lists), `section.registry.ts`, `section.photos.ts`, `section.upgrade.ts`, `section.links.ts`, `section.loading.ts`, `useDragScroll.ts` (drag a sideways row with the mouse; its `thumb` drives `SectionScrollHint`), `useScrollPin.ts` (scrolling down slides a sideways row right: see below).
   - `app/components/sections/`: `<type>/<Type><Layout>.vue` (one per layout), `SectionRenderer.vue`, `SectionFrame.vue`, `SectionPhoto.vue` (a photo, or a placeholder in the event's colours so the layout keeps its shape), `SectionPhotoCarousel.vue` (one photo spot that becomes a slideshow; autoplay off for `prefers-reduced-motion`), `SectionScrollHint.vue`, `SiteThemeScope.vue` (sets `--site-*` variables on a `.crephore-site` wrapper and plays the intro; `still` for thumbnails), `SectionThumbnail.vue`.
   - Text uses the same names in every type: `eyebrow` (small label above), `heading` (the section's h1/h2) and `body` (running text). `title` is for page titles only; never use it for section text.
2. Layout components only take `SectionLayoutProps<T>` (`content`, `background`, `options`, `occasion`). No API calls, stores or route access, so the same component works everywhere, including server rendering.
   - `occasion` is the page's event: `name`, `venue` (main venue's name), `startsAt` (UTC), `timezone`, `program` (`SectionProgram`), and a memorial's `bornOn` / `diedOn`. Details that belong to the event come from it and are never stored in section content, so they follow the event: the hero's heading, life dates, date and place, the countdown's target, and the program (the countdown's heading is the host's, else the event's name). The editor passes `eventOccasion(event, program)`, the published site builds it from `SiteDto`, previews without an event get `sampleOccasion()`. Date helpers take only `OccasionTime`.
3. Style only with site-theme variables (`bg-(--site-bg)`, `text-(--site-on-primary)`, `font-(family-name:--site-font-heading)`, `rounded-(--site-radius)`, …) and `backgroundStyles`. Never use the Crephore app theme (`bg-primary`, `text-foreground`, …) inside a section. The one exception is the white print border of photo frames (polaroids, mats).
   - Never use the raw `--site-primary` or `--site-secondary` as text. Use the contrast-checked versions (`--site-primary-text`, `--site-secondary-text`, `--site-secondary-on-primary`, `--site-primary-on-secondary`, `--site-secondary-on-photo`, `--site-on-*`). New brand-coloured text needs a checked variable in `siteThemeVars` (via `ensureContrast`) and a case in `test/nuxt/site-theme/useSiteTheme.test.ts`.
   - Every section uses `backgroundStyles[background]` the same way: `eyebrow` for small labels, `brandText` for headings and names, `root` / `muted` for long running text, `button` for buttons (`--site-button-<background>`; never assume which colour is dark), `accent` for small highlights (a text colour, so shapes use `bg-current` / `currentColor`), `avatar` for a missing photo's stand-in. Other drawn shapes use the text colour at low strength (`border-current/15`, `bg-current/20`).
   - Responsive styles use container queries (`@sm:` … `@2xl:`, against `SiteThemeScope`), never viewport breakpoints (`sm:`, `md:` …), and never name things `sm`/`md`/`lg`/`xl` (the check reads `xl:` in an object key as a breakpoint); `test/nuxt/sections/responsive.test.ts` enforces this. Use `@2xl:` where you would use `sm:`, and `@3xl:` for stacked to side by side.
4. Backgrounds: each layout lists its `backgrounds` (first = default), always all four (Light, Primary, Secondary, Photo); a layout's name never assumes a photo. Layouts with their own photos never start on `photo`; paper-on-a-colour layouts start on `secondary`. The picker shows them in `inPickerOrder`. `changeSectionLayout` moves a background that is still the old layout's default to the new default and keeps one the host picked. Without a photo, Photo renders exactly like Primary (`resolveBackground`).
   - Content frame: every section but the hero lines up with one column, at most 1280px wide: its sides come from `--site-edge` (`px-(--site-edge)` on the frame or the outer side of a full-bleed half, `ps-` / `pe-`), the gutter (`--site-gutter`: 28px, 48px from 672px, 64px from 1024px) or more on wide pages, set in `tailwind.css`. Never give a layout its own side padding or a 1024px / 1152px cap; narrower reading widths (`max-w-2xl` … `4xl`, padded with `--site-gutter` when they pad) sit centred inside the column (`content-frame.test.ts`). `--site-edge` measures the page, so never use it inside another container. The hero keeps its own padding and has no shared max width: each hero layout decides its own, and may have none.
   - Layouts never draw backgrounds: they wrap their content in `SectionFrame` and only position things. The frame clips with `overflow-clip`, never `overflow-hidden` (which makes a scroll container, so `sticky` children stop sticking); anything that wraps sections does the same (`PreviewFrame` does).
   - On the photo, the frame `overlay` must cover wherever text sits (`full`, or `overlayFor(position)` when the text has a known place; `none` only when the text has its own solid card). Text there is always light, checked against the brightest photo under the overlay, lightened when needed (`lightenUntil`), never darkened. Elements with their own surface keep their own colours.
5. Photos: always keep the background photo and the layout photos as separate fields, in every section type. Never let one photo field serve both.
   - `backgroundPhoto`: optional, works with every layout, passed to `SectionFrame` as `image-url`, shown only on the Photo background, never inside a layout.
   - `layoutPhotos` (ordered): shown only inside the layout through `SectionPhoto` / `SectionPhotoCarousel`, never as the background; missing ones show a placeholder. A layout shows up to its `layoutPhotoCount`; content stays the same across layouts. Types whose photos belong to items (people) have no `layoutPhotos` and `layoutPhotoCount` 0. `section.photos.ts` reads and sets photos without per-type cases.
   - Photos load lazily except in the page's first section: `SectionRenderer` provides its `priority` (`sectionPriorityKey`), and `SectionPhoto`, `SectionPhotoCarousel` (slides after the first always lazy), `SectionFrame`, `PersonPhoto` and `ProgramVenuePreview` use `:loading="usePhotoLoading()"` and `decoding="async"`. Every new section image must do the same (`photo-loading.test.ts`).
6. Content fields: each type lists every field its layouts can use (`<type>Fields`; `list.field` for a list item's field, e.g. `timeline.photo`; photos aren't fields). Each layout lists the fields it shows (`fields`), needs (`required`) and labels differently (`labels`). Content a layout doesn't show is kept for layouts that do.
   - `section.fields.ts`: `layoutFields<F>(layout)` (`uses`, `requires`, `label`), `missingFields`, `missingNotes` ("This layout needs …"). Content a layout doesn't show gets no note: the editor only offers the layout's fields. Editors whose layouts differ (about, people, message) take `:layout`, show a field only where `fields.uses(…)` and pass `:required="fields.requires(…)"`.
   - Requirements only ever warn, never block: "Required" on the empty field, `WebsiteSectionNotes` in section settings, an amber dot in the section list, and a warning under the save bar (`websiteWarnings`) saying publishing still works.
7. Options: placement is a layout option, not a separate layout (`textPosition`, `photoSide`, `textAlign`, …); give most layouts at least one (a layout may have none, e.g. the dress code's strip, pill and note). Options are defined once in a catalogue and layouts pick theirs by key.
   - `allSectionLayoutOptions` holds options several types share with the same meaning (an option moves there when a second type needs it); `<type>SectionLayoutOptions` holds the rest, with `<type>LayoutOptionCatalogue` and `<Type>LayoutOptions<K>`. A key is never in both (`layout-options.test.ts`); two types may each have their own option with the same key.
   - In the registry each layout lists its options in display order: `options('titleAlign', ['columns', { choices: columnChoices('2', '3'), default: '3' }])` (overrides: label, choices, default).
   - Components type options from the same keys, with no casts: `defineProps<SectionLayoutProps<'program', ProgramLayoutOptions<'titleAlign' | 'showTime'>>>()`. `options` is always complete; use `positionClasses` for 3×3 positions.
   - The editor shows options as `WebsiteChoiceGroup` cards, or a dropdown with `control: 'select'` for long lists; a choice's `group` puts it under a heading.
   - `changeSectionLayout` keeps the section's other fields and carries over an option the host changed when the new layout has it and offers the value; the rest take the new defaults. Saving keeps only the layout's own options (`withLayoutOptionsOnly`).
8. Stored keys and versions: type, layout, option and background keys and option values are stored on saved sections, so never rename them. Type and layout keys are listed in the API's `WebsiteKeys` (`../crephore-backend`, `Features/EventWebsites/WebsiteKeys.cs`), which rejects unknown keys on save.
   - Each type has a `contentVersion`, saved with its content. When its fields change, bump it and add an upgrade step in `section.upgrade.ts` (`upgradeSectionContent`, one step per version). Content is upgraded where it enters the app: `websiteFromApi` and `EventSitePage` (published sites aren't re-saved).
   - A removed layout maps to its replacement in `currentLayoutKey` (`section.registry.ts`, applied by `websiteFromApi` and `EventSitePage`), with an API migration for saved ones.
   - Sideways rows (about timeline cards and polaroids, people carousel, program horizontal timeline, the filmstrip hero and the silhouettes on phones) follow the page's scroll with `useScrollPin(content, row)`: once the row reaches the screen, the content (one wrapper element) is pinned while scrolling down slides the row right, one pixel for one, and up slides it back; swiping or dragging it scrolls the page to match. The layout puts `<div v-if="space" :style="space" />` right after the content (the room it slides through; a sticky element only travels within its parent's content, so padding wouldn't do). Browser only; never in a `still` scope (thumbnails, `stillScopeKey`) or with reduced motion. Pinned content stops below `--site-sticky-top` (px; the editor's preview sets the dashboard header's 64px). A new sideways row does the same.
9. Every link a section renders goes through `safeHref` (`section.links.ts`): only `#…`, `http(s):`, `mailto:` and `tel:` become links.
10. Pages render sections with `SectionRenderer` inside `SiteThemeScope`; never import layout components directly. Never set `--site-*` variables on `:root`. `SectionThumbnail` (pickers; not interactive) renders its section at desktop width, scaled, only once near view (`useElementVisibility`, 300px margin; right away without IntersectionObserver) and keeps it rendered.
11. Adding a layout:
    - One component per layout, named after its key (`overlay-card` → `hero/HeroOverlayCard.vue`); never let one component serve several layouts. Reuse the shared non-layout pieces next to them (e.g. `HeroText`, `CountdownHeading`, `MessageBody`, `AboutChapter`, `PersonPhoto`, `ProgramHeading`, `ProgramVenues`) so layouts stay consistent.
    - Register it in `<type>.registry.ts` with a description, `backgrounds`, `fields` (`required` / `labels` where they differ; `section.registry.test.ts` and the layout tests check them), options (add new ones to `<type>.options.ts` first, or `allSectionLayoutOptions` when another type has it) and `layoutPhotoCount` (the editor shows that many photo fields).
    - Add its key to the API's `WebsiteKeys`, and check it in the playground (`/admin/section-types/playground`) across options, backgrounds, colour presets, fonts, corners, device sizes and event timing (`Playground<Type>Content.vue` holds each type's content controls; `PlaygroundOptionalPhoto.vue` / `PlaygroundPhotoField.vue` the photos).
12. Adding a section type: `features/sections/<type>/` with its content interface (with `backgroundPhoto`, and `layoutPhotos` if layouts have photos) added to `SectionContentMap`; its registry with `defaultContent` and `contentVersion: 1`, added to `sectionRegistry`; `<type>.options.ts`; its keys in the API's `WebsiteKeys`; `components/sections/<type>/`; its starting event details in `event-website.ts` (`eventDetails`); `Website<Type>Fields.vue` and `Playground<Type>Content.vue`.
13. Type-specific rules (registries and component comments describe each layout):
    - Hero: `HeroText` reads the heading (`occasion.name`, the h1), date and venue from `occasion`. `lifeDates` (`full` / `years`, unset for none; `formatLifeDates`) shows once both dates exist; the editor offers it only for memorials, whose new hero starts on `years`. Every hero layout fills the screen: its frame is `min-h-[max(var(--site-screen-height),36rem)]` (never under 36rem, for short phones and phones held sideways) with the content centred in the extra height, or a photo that grows into it (the banner, Split stacked on phones). Full (`fullscreen`) places its text across the full width (side padding `--site-hero-edge`: the sections' gutter until their 1280px column is full, then a quarter of the extra width on each side), and with the text off-centre fades the photo into a solid colour at the text's edge, clear by 45% across, with the overlay kept near the text (full over 40%, clear by 65%) at the least strength text needs (`--site-photo-overlay-edge`; every other photo overlay, `--site-photo-overlay`, is 10 points stronger, `PHOTO_OVERLAY_BOOST`, so the primary's tint shows) so the far side stays untouched (`SectionFrame` `edge`; `--site-photo-edge`: the primary when the light text and headings read on it, else `--site-primary-900`). `SiteThemeScope` sets `--site-screen-height` (`screenHeight`: `100svh` on the site and in previews, `750px` in thumbnails).
    - Countdown: headed by its optional `heading` (the editor's placeholder is the event's name), else `occasion.name` (`countdownHeading`; no upgrade step, so saved sections without one read as before); counts to `occasion.startsAt`. Only the invitation (`invitation`: no icon in the eyebrow, two layout photos, the small one framed in the section's colour) shows a message (`body`, "Message (optional)"); `WebsiteCountdownFields` takes `:layout` for it. `useCountdown` ticks from mount only, so server rendering and the first render show "--"; once started everything shows 0. Dates are formatted in the occasion's timezone (`formatOccasionDate`).
    - About: story layouts never show the timeline; timeline layouts (`layoutPhotoCount` 0) show the body as an intro and require chapters. Both are kept when switching.
    - People: photos belong to the people (`PersonPhoto` shows `personInitials` without one); each person has a stable `id`; every layout requires `people`.
    - Dress code (`dress-code`): every full layout's first option is Title and text (`textAlign`, with right added: the eyebrow, heading and attire, and the description, colours and "please avoid", together), `aligned()` in the registry, defaulting to the layout's own look (stacked layouts centred, side-by-side ones left); side-by-side layouts align within their text column, the art keeping its side. Split colour alone has separate Title (`titleAlign`, its colour half) and Text options. Components type them with `DressCodeAlignedOptions<K>`; the shared pieces take `align` (`justifyClasses` / `blockAlignClasses` in `section.options.ts`). What guests wear: `attire` (the attire motif in the host's own words, read with `attireOf`; optional in every layout, which leaves it out without one; until content version 2 it was a preset key, see `section.upgrade.ts`), `description`, `colours` and `avoidColours` (up to `dressColourMax`, 5, each `{ id, name, hex }`; the editor notes the limit above the colours to wear) and inspiration photos (`layoutPhotos`, up to `inspirationPhotoMax`). Three compact one-line layouts first (`strip`, `pill`, `note`: no description or photos), then nineteen full ones, each fitting five colours (the formality scale was removed with the presets; saved ones show as `palette`). Host colours are content, so swatches use them inline (`:style`), and text on one uses `textOnColour`; pale swatches get a thin `border-current/15`. Shared pieces in `components/sections/dress-code/`: `DressCodeHeading`, `DressCodeDescription`, `DressCodeSwatches`, `DressCodeAvoid`, `DressCodeHanger`. The silhouettes layout (key `hangers`, from when it was a clothes rail) shows one outfit drawing per suggested colour from `assets/images/dress-code/` (white shapes on transparency, used as CSS masks so their details are cut-outs), each a flat fill in its colour with a crisp hairline (on the light background a darker shade of the figure's own colour; on the others white when the background is close to black, else a darker shade of the background, worked out in CSS from its variable), so it shows even on a background of the same colour; the tuxedo's pocket square is filled in. A new section starts on `sampleDressCode` (colours and a description, no attire motif).
    - Program: shows `occasion.program` (see "Event Program"), never stored in the section. Items keep the host's order, never sorted. The program's `venue` shows under the heading when every item shares it, else each item shows its own. On the published site a program section without items is left out. Every layout has `showTime` (large-time layouts show the item's number instead, `programMarker`), ends with `ProgramVenues` (headed by `venuesEyebrow` / `venuesHeading`, each left out when empty), and, except fixed ones, has `titleAlign` first. Day labels show just the date, never "Next day". A note is always smaller and `muted` beside its venue. Program headings are never bold nor in capitals, and every `ProgramHeading` `look` is the usual heading size. The vertical title's old "Vertical left" (`titleAlign: 'vertical'`) was removed; saved ones read as its default, left. "See map" (`ProgramVenueMapLink`) is the only map link opened directly in a new tab.
    - List limits: `aboutTimelineMaxItems`, `peopleMaxItems`, `programMaxItems`.
14. Tests in `test/nuxt/sections/` (`<Type>Layouts.test.ts`): each layout renders its content, shows each photo (or placeholder) only where it belongs, hides missing optional content, applies each supported background, and each option changes the placement. `CountdownLayouts.test.ts` freezes the clock with `vi.useFakeTimers({ toFake: ['Date'] })`.

## Event Program
The event's schedule belongs to the event (the API's `event_program_items`), not to a website section: every program section of its website shows it, and guests see changes without publishing again. Each item happens at one of the event's venues or none.

1. Data: `features/event-programs/`.
   - `event-program.type.ts`: `EventProgram` (items with `id`, `date` `"2027-02-14"` in the event's timezone, `startTime` / `endTime` `"15:00"` or null (an end before the start means after midnight), `title`, `description`, `venueId`, comma-separated `speakers`), `UpdateEventProgramRequest`, `EventProgramDraft`.
   - `event-program.api.ts`: `getEventProgram`, `updateEventProgram` (`PUT /events/{id}/program` replaces the whole program, saved items by id).
   - `event-program.ts`: `programFromApi`, `mapProgramToRequest` (trimmed, blanks as null), `isSameProgram`, `sectionProgram(program, venues)` (what sections show), `programErrors` (the API's rules and messages, keyed `items[2].title`), `programItemLimits`.
2. The event page loads the program and venues with the event and owns them: the Program tab saves the program (`@saved` updates the page), and the Website tab gets `sectionProgram(program, venues)` for the occasion. When a saved change removes venues, the page reloads the program (the API moved their items to the main venue).
3. `EventProgramTab.vue`: items in guests' order, reordered by drag or Arrow Up/Down on a handle. A day is picked from `programDayChoices` (the event's days plus the day after, and the item's own date when it's another). The venue select ends with "No venue" and "Add a venue…" (`EventAddVenueDialog`, saved right away; `venues-saved` updates the page). New items start at the main venue; items whose venue was removed move to it, as the API does. Saving checks `programErrors` first and shows each error beside its item, as with the API's. Read-only without Owner access.
4. Tests: `test/nuxt/event-programs/`, `test/nuxt/events/EventProgramTab.test.ts`.

## Event Venues
Where an event happens: a list per event (the API's `event_venues`), up to 10, in the host's order; the first is the **main venue**, whose name the dashboard, the hero and the intros show (`Event.venueName`, `SiteDto.venueName`, "" without one). The event itself has no venue fields; program items pick a venue by id. There's no venue section: the website shows venues inside program sections.

1. Data: `features/event-venues/`.
   - `event-venue.type.ts`: `EventVenue` (`name`, optional `address`, `googleMapsUrl`, `appleMapsUrl`, `latitude` / `longitude`, `photoUrl`, `notes`), `UpdateEventVenuesRequest`, `EventVenueDraft`.
   - `event-venue.api.ts`: `getEventVenues`, `updateEventVenues` (`PUT /events/{id}/venues` replaces the list, saved venues by id; a removed venue's items move to the new main venue).
   - `event-venue.ts`: `venueFromApi`, `mapVenuesToRequest`, `isSameVenues`, `venueErrors` (keyed `venues[1].name`), `isGoogleMapsUrl` / `isAppleMapsUrl`, `pinLinkOf`, `mapPreviewUrl` (always Google Maps' keyless embed at the pin: Apple Maps refuses to be framed and MapKit JS needs a developer token), `eventVenuesMax`, `venueLimits`.
2. Map pins: hosts never place a pin; they paste a Google Maps and/or Apple Maps link. `server/api/map-pin.get.ts` (`GET /api/map-pin?url=…`, this app's own Nitro route, cached a day per link; called by `map-pin.api.ts` `getMapPin` with `$fetch`, not the Crephore API) reads the pin out of the link, following short links one hop at a time (`server/utils/map-pin.ts`: `isMapLink` only opens https links on Google's and Apple's map hosts, checked on every hop). The pin is saved with the venue; clearing the links clears it.
3. `EventVenuesTab.vue`: a card per venue, edited with `EventVenueFields.vue` (shared with the add-venue dialog), "Make main venue" (moves it first) and "Remove venue" (confirmed when items use it, saying where they move). Venues added from the Program tab join the list without losing edits here. Errors show beside the field and open the venue. Read-only without Owner access.
4. Tests: `test/nuxt/event-venues/` (incl. map-pin parsing and redirects), `test/nuxt/events/EventVenuesTab.test.ts`.

## Website Editor
Hosts build their event's website in the event page's Website tab (`dashboard/events/[id]/_components/`).

1. Flow: `EventWebsiteTab.vue` loads the saved website (skeleton, "Try again" on failure) and opens `website/WebsiteEditor.vue`, or without one `EventWebsiteStart.vue` ("Start from a template", a placeholder for now, or "Start from scratch"). "Start over" (confirmed when there's something to lose) deletes the saved website and goes back to the choice.
2. Data: `features/event-websites/`.
   - `event-website.type.ts`: `EventWebsiteDraft` (`theme` + `sections` in page order), `WebsiteSection` (a `Section` plus the editor's `key`, saved `id`, `isVisible`, and `visibility`, kept as loaded with no editor control yet), `EventWebsite` / `UpdateEventWebsiteRequest`.
   - `event-website.api.ts`: `getEventWebsite` (`data` null when none), `updateEventWebsite` (saves the whole website), `deleteEventWebsite`, `publishEventWebsite`.
   - `event-website.ts`: `createBlankWebsite`, `defaultWebsiteTheme`, `eventOccasion`, `withSampleProgram`, `createWebsiteSection(type, event)` (default content plus `eventDetails`; never the event's name, date, venue or program), `duplicateWebsiteSection`, `moveItem`, `websiteWarnings`, `websiteProblem`, `websiteFromApi`, `mapWebsiteToRequest`, `isSameWebsite` (compares what would be saved), `withSavedIds` (assigns ids by key after a save, so edits made while saving stay).
   - Saving works like the Details form; the save bar reads "Not saved yet" / "You have unsaved changes" / "All changes saved". A blank page never saved has nothing to save.
   - Edits always replace objects (`{ ...section, … }`), never change them in place: the saved copy shares objects with the draft until they change.
   - Publishing: guests only see the website as last published. The save bar shows "Not published", "Live" or "Live · changes not published" (`hasUnpublishedChanges` from the API, or unsaved edits). "Publish" / "Publish changes" saves first, then publishes, and needs a visible section. "View website" opens `urlOf` once published. "More" has Unpublish (confirmed) and Start over (also takes the site offline).
   - Unused photos are dropped when saving, never while editing (`withoutUnusedPhotos`, applied by `mapWebsiteToRequest`): the background photo unless the background is Photo, and layout photos past `layoutPhotoCount`. The draft keeps them so switching back shows them again; item photos (chapters, people) are content and always kept. An unused photo isn't an unsaved change.
   - One hero per page: exactly one hero section, shown or hidden (`websiteProblem`, same rule and messages as the API). Otherwise the save bar says why and Save and Publish are disabled (`save()` checks too). The add dialog doesn't offer a second hero and the hero can't be duplicated; deleting it is allowed, but the page then needs a new one before saving.
3. Editor layout: a panel with Sections and Style tabs (sticky, `h-16`: under the app's sticky header, `top-16`, and from `xl`, where the panel scrolls by itself, at its top; an open section's title row sticks right under them, `top-32` / `xl:top-16`) beside a live preview (`PreviewFrame` + `WebsitePreview`) in the event's theme with the event as the occasion.
   - `WebsiteSectionList`: drag or Arrow Up/Down on the handle, eye to hide, menu to move, duplicate or delete (confirmed). "Add a section" (`WebsiteAddSectionDialog`) inserts after the section being edited, else at the end, and opens its settings with the layout picker open. Clicking a section in the list or preview opens `WebsiteSectionSettings`: layout (`WebsiteLayoutPickerDialog`, thumbnails in the section's own content), placement options (`WebsitePositionPicker` for 3×3, else `WebsiteChoiceGroup`), background (`WebsiteBackgroundPicker`; the background photo field only on Photo), one photo field per `layoutPhotoCount`, then the text (`Website<Type>Fields.vue`).
   - Shared inputs (`website/`): `WebsiteTextField`, `WebsiteTextareaField`, `WebsiteListField` (drag handles with Arrow Up/Down, remove, "Add …" up to `max`, `#item` slot, `data-<name>-item` / `data-<name>-handle` hooks, `keyOf`); `required` marks "Required" while empty. Each `Website<Type>Fields.vue` keeps its own rule for an emptied field (removed, or kept as "").
   - Picking one of a few choices uses `WebsiteChoiceGroup` (separate cards, the chosen one with a primary border, bold label and check badge), not a joined toggle group.
   - Text from the event (hero heading, life dates, date, place) is shown read-only in `WebsiteEventFields.vue` under an info `CAlert` (`role="note"`) with an "Edit details" link. Never add an editable field for it, and never store it in section content.
   - `WebsiteProgramFields.vue` edits the section's own text in a Program group (eyebrow and heading, then the program read-only under a `CAlert` linking to the Program tab) and a Venues group (the venues' eyebrow and heading, then a `CAlert` linking to the Venues tab). The preview fades a program section without items ("No schedule yet"); thumbnails use `withSampleProgram(occasion)` while the event has no program.
   - Photos (`WebsitePhotoField`): "Upload photo" checks the type (`photoContentTypes`: JPG, PNG, WebP, GIF), shrinks the photo in the browser (`features/media/photo.ts` `shrinkPhoto`: longest side to 2400 px, WebP at 0.85 quality with JPEG/PNG fallback; GIFs, small photos, undecodable files and results that wouldn't be smaller upload as they are), then checks the 10 MB limit (`photoMaxBytes`, checked again by the API), uploads right away (`POST /events/{id}/media`, `media.api.ts` `uploadPhoto`) and stores the URL in the section's content; the section is saved with the website.
   - Style: the shared `ThemeControls`; "Play intro" plays it in the preview (`introKey`). The playground has the same controls.
4. Hidden sections stay in the editor, faded in the preview, and are not shown to guests. Links inside sections don't navigate in the preview.
5. Editor chrome on the preview (selection outline, section labels) uses a fixed editor blue (`sky-500`), never the app's or the site's colours, so it can't be mistaken for part of a section. The sections inside keep the site theme.
6. Tests: `test/nuxt/event-websites/` (`event-website.test.ts` incl. save mappers, `event-website.api.test.ts`, `WebsiteEditor.test.ts`, `EventWebsiteTab.test.ts`), `test/nuxt/media/`, `test/nuxt/sites/`.
