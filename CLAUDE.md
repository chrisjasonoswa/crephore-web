# Crephore Web: Agent Instructions

This file is the source of truth for this repository's structure, API, auth, form, and testing conventions.
Follow it for every change, and update it when conventions change.

The structure mirrors the Zao POS web app (`~/Projects/zao/zao-pos-web`). When something is not covered here, follow how that project does it.
Intentional differences from zao: SSR for public pages (zao is `ssr: false`), the `landing` layout and `site-theme/` for the public site and event websites, `config/navigation.ts` instead of inline sidebar data, and the `c-`/`C` prefix instead of `z-`/`Z`.
The API is `../crephore-backend` (see its `CLAUDE.md`); keep types in sync with its DTOs.

---

## Tech Stack
- Nuxt 4 (`app/` directory), Vue 3, TypeScript
- UI: shadcn-vue (`app/components/ui`, no prefix, auto-imported), Tailwind CSS 4, `@lucide/vue` icons
- State: Pinia (`@pinia/nuxt`)
- HTTP: axios through `app/lib/axios.ts`
- Forms: vee-validate + zod (`@vee-validate/zod`, zod 3 syntax: `z.string().email()`)
- Toasts: vue-sonner through `cToast()` in `app/lib/cToast.ts`
- Drag to reorder: `vue-draggable-plus` (SortableJS). For vee-validate field arrays pass `customUpdate`: put Sortable's DOM move back and call `useFieldArray().move(oldIndex, newIndex)` (no field array uses it today; the editor's lists, `WebsiteSectionList.vue` and `WebsiteListField.vue`, reorder plain arrays the same way)
- Tests: vitest + `@nuxt/test-utils` (`environment: 'nuxt'`)
- Package manager: pnpm (version pinned in `package.json` `packageManager`; dependency build scripts allowed in `pnpm-workspace.yaml` `allowBuilds`, as in zao). Do not use npm or commit a `package-lock.json`.

## Project Structure
- `app/features/<feature>/`: the data side of one feature (types, API calls, stores, registries)
  - `<feature>.type.ts`: request/response types mirroring the backend DTOs
  - `<feature>.api.ts`: one function per endpoint plus a `<Feature>ApiRoutes` object; only uses `get/post/put/patch/del` from `~/lib/axios`
  - `<feature>.store.ts`: Pinia setup store (`use<Feature>Store`), when state is shared across pages
- `app/pages/`: routes
  - Route groups organise pages without changing the URL:
    - `(auth)/`: `sign-in`, `sign-up` (use the `auth` layout)
    - `(dashboard)/`: signed-in pages, `dashboard/**` and `admin/**` (use the default layout; set `area` in `definePageMeta`)
    - `index.vue`: the public landing page (uses the `landing` layout)
  - A page is `<route>/index.vue`; its page-only pieces live next to it in `_components/`:
    - `<Name>Form.vue` for the form component, `<Name>FormFields.vue` for reusable field groups
    - `<name>.form.schema.ts` with the zod schema, `<name>FormInitialValues`, and `mapFormValuesTo<Request>()` mappers
  - `_`-prefixed folders and `.ts` files under `pages/` are not routes (`pages:extend` hook in `nuxt.config.ts`).
- `app/components/`: app shell components, as in zao
  - `AppSidebar.vue` (composes `NavMain.vue` per nav group and `NavUser.vue` for the user menu and sign out), `SiteHeader.vue` (breadcrumbs, search, `ModeToggle.vue`)
  - Brand and page pieces: `AppLogo.vue`, `AppLogoMark.vue`, `PagePlaceholder.vue`, `landing/*` (subfolder names prefix the component name, e.g. `LandingFeatureCard`)
  - `custom/c-<name>/C<Name>.vue`: reusable building blocks, registered without a path prefix (Crephore's equivalent of zao's `custom/z-*/Z*`)
    - `c-form/CFormTextField.vue`: vee-validate field (label, input, first error, optional `#description` slot); `type="password"` renders `CPasswordInput`; `#addon-start` / `#addon-end` put text or icons inside the input (shadcn `InputGroup`, e.g. the subdomain's `.crephore.com` suffix)
    - Help text: every `CForm*Field` takes a `#field-info` slot, shown in a popover behind an info icon next to the label (`c-form/CFormFieldLabel.vue` + `CFormFieldInfo.vue`, zao's `ZFormFieldLabel` / `ZFormFieldInfo`). Use it to explain what a field is for; use `#description` only for a short hint that should always be visible
    - `c-form/CPasswordInput.vue`: password input with show/hide toggle
    - `c-header/CPageHeader.vue`: page title, description (or a `#description` slot for richer content, e.g. an event's date), `#actions` slot
    - `c-tabs/CPillTabs.vue`: a shadcn `Tabs` list as rounded pills (active = primary); use it inside `<Tabs>` in place of `TabsList` for a page's main tabs
    - `c-toast/CToast.vue`: the toaster, mounted once in `app.vue`
    - `c-alert/CAlert.vue`: an alert in the shared toast and alert styles (zao's `ZAlert`): `type` (`info`, `warning`, `error`, `success`) picks `toastAndAlertStyles[type]`'s colours and icon; `icon` replaces the icon (null: none); optional `title`, `description` (HTML, only Crephore's own text) and `size` (`default`, `sm`); the default slot for richer content such as links; `w-fit` unless given a `class`. Use it for every alert in the app, never the bare shadcn `Alert`.
    - `c-data-table/`: paged list tables ported from zao's `z-data-table` (`CDataTable`, `CDataTableCard`, column defs `CDataTableTextColumn` / `CDataTableDateTimeColumn`). Server-side paging, sorting and search; add/edit/delete through `CDataTableFormDialog` (or `onUpdateItemClicked` to edit elsewhere, like `onAddItemClicked`); each row's actions are labelled buttons ("Edit", "Delete"), not a "⋯" menu, so they're easy to find (unlike zao), and `updateItemLabel` renames the edit button; optional `expandedRowComponent` for per-row panels; exposes `reload()`
    - `c-modal/CConfirmationModal.vue`: confirm before destructive actions outside the table dialog
    - `c-date-time/CDateTime.vue`: an event time or range in the event's timezone, with a muted "(Manila, GMT+8)" for viewers in another timezone (see `date.ts` below)
    - `c-form/CFormSelectField.vue` (`clearable` sends `null`), `c-form/CFormTextareaField.vue`
    - `c-form/CFormCheckboxListField.vue`: an array of checked option values, with optional search and per-option `description` / `hint` (e.g. picking a group's events)
    - `c-form/CFormDateField.vue`: a date without a time (`"1948-02-14"`, empty when unset), the same date picker with month and year dropdowns, bounded by `min` / `max` (default 1900 to today); `clearable` adds a button that empties it (e.g. a memorial's dates of birth and passing)
    - `c-form/CFormDateTimeField.vue`: the shadcn-vue date picker (Calendar in a Popover) plus a time input (`clearable` adds a button that empties both, e.g. an event's optional end); the value is a wall-clock string (`"2027-06-12T15:00"`) sent as it is with the event's `timezone`; the API converts it to UTC. Use it for every date/time field instead of `<input type="datetime-local">`
  - `ui/`: shadcn-vue components. Add them with `pnpm dlx shadcn-vue@latest add <name>` and do not edit them by hand.
    - The components style state with `data-open:`, `data-checked:`, `data-active:`, `data-horizontal:` … while reka-ui sets `data-state` / `data-orientation`. `assets/css/tailwind.css` maps those variants with `@custom-variant` (each matches reka's attribute or the plain one); keep that list in sync when adding components that use another state variant. Without it switches, checkboxes and active tabs look off, tabs don't stack, and overlays don't animate.

## Event Websites (guests)
Guests open an event's website at `<subdomain>.<site domain>`: `ana-and-marco.crephore.com`, or `ana-and-marco.localhost:3000` in development (Chrome, Edge and Firefox send `*.localhost` to this machine; Safari may not).
1. The site domain comes from `runtimeConfig.public.siteBaseUrl` (`NUXT_PUBLIC_SITE_BASE_URL`, default `http://localhost:3000`); `features/sites/site.ts` (`siteAddress`, `siteSubdomainOf`) and `useSiteAddress()` build and read addresses from it.
2. Routing by host (`app/router.options.ts`): on an event's subdomain the app has one route, `/`, rendering `pages/_site/EventSitePage.vue` without a layout (any other path redirects to `/`); on the site domain itself (and `www`) it is Crephore with the pages in `pages/`. It runs per request on the server and once in the browser.
3. `EventSitePage` loads the published website (`features/sites/site.api.ts`, `getSite` → `GET /sites/{subdomain}`, no sign-in) with `useAsyncData`, so it is server-rendered (guests and link previews get the whole page, and the browser never calls the API). It renders the sections with `SiteThemeScope` + `SectionRenderer`, titled with the event's name; unpublished and unknown addresses get a 404 "This website isn't available" page.
4. `/` is server-rendered, not prerendered: one prerendered page would answer for every event's address.
5. The API client never toasts on the server, nor for `/sites/…` requests (`SILENT_URL_PREFIXES`).

## API Conventions
1. Every endpoint returns `ApiResponse<T>` (`{ success, data, message, errors }`); type API functions as `post<ApiResponse<T>>(...)`.
2. Never call axios directly from pages or components; add a function to `features/<feature>/<feature>.api.ts`.
3. The API client already shows the API's `message` as an error toast (except for `SILENT_URLS`), so callers should not toast errors again. Use `applyServerErrors(form, getApiErrors(error))` to also show field errors inline.
4. The API URL comes from `NUXT_PUBLIC_API_URL` (`.env`, see `.env.example`); never hard-code it.

## Auth
1. Auth is cookie-based. Login sets HttpOnly `accessToken` (30 minutes) and `refreshToken` (7 days) cookies that JavaScript cannot read; requests send them via `withCredentials`.
2. `useAuthStore` keeps `user` in memory plus an `isAuthenticated` flag in localStorage. The flag only drives route guarding; the API stays the authority.
3. Login (and sign-up, which logs in right after) calls `authStore.setAuth({ user })` from the login response.
4. The default (sidebar) layout calls `init()` on mount, which loads `GET /auth/me` and restores the user after a refresh.
5. Logout: `authStore.logout()` calls the API and always clears the local session, even if the API call fails.
6. Refresh, as in zao-pos-web (`lib/axios.ts`): a 401 (except from login, refresh and logout) calls `POST /auth/refresh` once and retries the request. Requests failing at the same time share one refresh (each refresh rotates the token). If the refresh fails, or the retry gets a 401 again, the session is cleared and the user is sent to `/sign-in?reason=session-expired`. Covered by `test/nuxt/auth/axios.refresh.test.ts`.
7. `auth.global.ts` sends signed-out visitors away from `protectedPaths` (`/dashboard`, `/admin`) and signed-in users away from `/sign-in` and `/sign-up`. It only runs on the client because the flag lives in localStorage. Add new signed-in areas to `protectedPaths`.

## List Pages
1. Lists use `CDataTable` inside `CDataTableCard`, like zao: a `<Feature>Table.vue` builds `tableProps` (`resourceName`, `columns`, `loadItems`, `addItem` / `updateItem` / `deleteItem`, `form` + `formInitialValues` + `formFieldComponent`, `mapItemToFormValues`).
2. Page-local files next to the table in `_components/`: `<name>.table.columns.ts`, `<name>.form.schema.ts`, `<Name>FormFields.vue`, and expanded-row panels when a table needs one.
3. One table per page. Data that organises a list sits beside it as a side panel that filters it, not on its own page or in `Tabs`: e.g. My events (`/dashboard/events`) has `EventGroupsPanel` (pick a group to filter the events table, add/edit/delete groups, including which events they hold, through `CDataTableFormDialog`). The panel is closed by default ("View groups" above the table opens it, the panel's close button hides it; the state is remembered per browser) and the selected filter is shown as a chip above the table. Events are only grouped here: the event form has no group field, a new event goes into the group selected in the panel (if any), and saving an event's details never changes its group (the API's update has no `eventGroupId`). The panel's note on what a group is sits right under its title. Separate lists that stand on their own become separate routes, as sidebar sub-items (`children` in `config/navigation.ts`) if they belong together.
4. Records that have more than one form's worth of settings get their own page instead of the edit dialog: e.g. an event (`/dashboard/events/[id]`). The table's "Manage" button (`onUpdateItemClicked` + `updateItemLabel`) and the name column link there; adding stays a quick dialog that then opens the new record's page (the host carries on there), and deleting stays in the table.
   - The page loads the record by id (skeleton while loading, "not found" empty state), names the breadcrumb with `useBreadcrumbTitle`, and splits its parts into `CPillTabs`: for an event, Details (the form, `[id]/_components/EventDetailsForm.vue`; a memorial also has optional "Date of birth" and "Date of passing", `bornOn` / `diedOn`, the passing not before the birth, sent as null for other types), Venues (`EventVenuesTab.vue`, see "Event Venues"), Program (`EventProgramTab.vue`, see "Event Program"), Website (`EventWebsiteTab.vue`, see "Website Editor") and Guests & RSVP (placeholder).
   - The active tab is in the URL (`?tab=website`; none for the first tab). Tabs with unsaved edits (Details, Venues, Program, Website) are `force-mount`ed and hidden when inactive, so the edits survive switching tabs.
   - The form saves with "Save changes" / "Discard changes" (disabled until something changes) in a save bar above it (`[id]/_components/EventSaveBar.vue`, also the Venues and Program tabs'; like the Website tab's: the error alert style with "You have unsaved changes." while there are any, success with "All changes saved." otherwise), resets to the saved record, and asks before leaving the page with unsaved changes (`onBeforeRouteLeave` + `CConfirmationModal`, and `beforeunload`).
   - An event's end is optional ("Ends" can be cleared; `endsAt` is null without one): its page shows just the start, and the Program tab's days run from its day to the day after.
5. When one part of the page changes data another shows, reload it: the table is re-created with a `:key` (the filter, plus a version bumped on changes, so it starts on page 1), and the panel exposes `reload()`. CDataTable also exposes `reload()`.
6. TanStack Table is pinned to v8 to match zao; do not upgrade to v9 without porting `c-data-table`.

## Sections
Sections are the building blocks of the event websites (Hero, RSVP, FAQ, …). They render in the admin playground, previews, the host editor and the public event site, so they follow strict rules.

1. Files:
   - `features/sections/section.type.ts`: `SectionBackground`, content shape per type (`SectionContentMap`), `Section` (with `options`), `SectionLayoutProps<T>`, `SectionOccasion` + `sampleOccasion()`, `OccasionTime` (just `startsAt` + `timezone`, what the date helpers take)
   - `features/sections/<type>/`: one folder per section type (`hero`, `countdown`, `message`, `about`, `people`, `program`), matching `components/sections/<type>/`. Each has `<type>.type.ts` (its content interface: `HeroContent`, `CountdownContent`, `MessageContent`, `AboutContent` with `AboutTimelineItem`, `PeopleContent` with `PersonItem`, `ProgramContent` with `ProgramItem` and `ProgramVenue`), `<type>.registry.ts` (its section type and layouts: `heroSection`, …) and, when it has logic, `<type>.helpers.ts`. The files directly in `features/sections/` apply to every type. Text uses the same names in every type: `eyebrow` (the small label above), `heading` (the section's h1/h2) and `body` (running text, when the type has any). `title` is for page titles only; never use it for section text.
   - `features/sections/section.cta.type.ts`: `SectionCta` (the button hero and countdown share)
   - `features/sections/countdown/countdown.helpers.ts`: the countdown's time maths and date formats (`countdownParts`, `countdownUnits`, `useCountdown`, `formatOccasionDate`, `calendarMonth`)
   - `features/sections/section.background.ts`: classes per background (`root`, `muted`, `eyebrow`, `button`, `brandText`, `avatar`: a filled stand-in for a missing photo, a soft tint of the section's colour with that colour's text: `--site-secondary-100` with the secondary text on secondary sections, `--site-primary-50` with the primary text otherwise; `avatarAccent`: the other brand colour as it reads on that tint, for a mark on it; `accent`: the theme's accent for small highlights, icons, ornaments, dots and rings, as a text colour, so shapes use `bg-current` / `currentColor`). Every section uses both brand colours the same way: `eyebrow` for small labels (eyebrows, roles, chapter labels, the signature) and `brandText` for headings and names (section headings, chapter headings, a person's name and bio). Light: secondary labels, primary headings. Primary: softer-primary labels, secondary headings. Secondary: softer-secondary labels, primary headings. Photo: like primary (soft light labels, secondary headings). Long running text (a message, a story, dates and venues) stays `root` / `muted`. Each colour is contrast-checked, so a too-light or too-dark brand colour is shifted the other way until it reads.
   - Content fields: each section type lists every field its layouts can use (`<type>Fields` in `<type>/<type>.type.ts`, on the type as `fields`; `list.field` names a list item's field, e.g. `timeline.photo`, `people.bio`; photos aren't fields: `backgroundPhoto` and `layoutPhotoCount` cover them). Each layout lists the ones it shows (`fields`), the ones it needs filled in (`required`) and any label that reads differently there (`labels`). Content a layout doesn't show is kept for layouts that do. `features/sections/section.fields.ts`: `layoutFields<F>(layout)` (`uses`, `requires`, `label`, typed by the type's field names) for the editors, `missingFields`, `hiddenFields`, and `fieldNotes` (the notes' wording, from the type's `fieldNames`: a word for text, one and many for a list, e.g. about's `timeline: ['chapter', 'chapters']`). Editors whose layouts differ or require something (about, people, message) take `:layout`, show a field only where `fields.uses(…)` and pass `:required="fields.requires(…)"`; the others show all their fields, which every one of their layouts uses.
   - What a layout requires only ever warns, never blocks: the field (or list) is marked "Required" while empty; section settings show `WebsiteSectionNotes` above the text ("This layout needs at least one chapter.", and "This layout doesn't show your 3 chapters. They're kept for layouts that do."); the section list marks the section with an amber dot (and "missing content its layout needs" for screen readers); and a warning under the save bar lists the visible sections missing content (`websiteWarnings` in `event-website.ts`), saying publishing still works since layouts show placeholders. Requirements today: timeline layouts need a chapter, people layouts a person, message layouts the message.
   - `features/sections/section.options.ts`: layout placement options (`SectionLayoutOption`), the catalogue types and `pickLayoutOptions`, the shared choice sets (`positionChoices` 3×3, `sideChoices`, `alignChoices`, `alignWithEndChoices`, `aboveBelowChoices`, `showHideChoices`; literal values, so options can be typed), `resolveLayoutOptions`, `positionClasses`, `alignClasses`, `overlayFor`
   - Layout options are defined once, in a catalogue, and layouts pick theirs by key:
     - `features/sections/section.layout-options.ts` `allSectionLayoutOptions`: the options several section types share with the same meaning (`textAlign`, `photoSide`, `photoPosition`, `textPosition`). An option moves here when a second type needs it.
     - `features/sections/<type>/<type>.options.ts` `<type>SectionLayoutOptions`: the rest of that type's options (program: `titleAlign`, `showTime`, `timeColumn`, `columns`, …), plus `<type>LayoutOptionCatalogue` (both merged) and the `<Type>LayoutOptions<K>` type. Types may each have their own option of the same key (people's and program's `columns`), since a section only switches layouts within its type; a key is never in both the shared catalogue and a type's (`layout-options.test.ts`).
     - In `<type>.registry.ts`, each layout lists its options in display order: `options('titleAlign', 'showTime', ['columns', { choices: columnChoices('2', '3'), default: '3' }])`, a key or a key with overrides (label, choices or default; e.g. a layout's default where it put things before the option existed).
     - Layout components type their options from the same keys: `defineProps<SectionLayoutProps<'program', ProgramLayoutOptions<'titleAlign' | 'showTime'>>>()`, so `options.titleAlign` is `'start' | 'center' | 'end'`, with no casts (a layout that adds a choice widens its type itself, e.g. the vertical title's `'vertical'`).
   - `features/sections/section.layout.ts` (`layout()`, which defines a layout with its component loaded on demand, and the shared background lists `onColour`, `onPaper`, `colours`) and `section.registry.type.ts` (`SectionTypeDefinition`, `SectionLayoutDefinition`), used by every `<type>.registry.ts`
   - `features/sections/section.registry.ts`: puts the types together (`sectionRegistry`, in the add dialog's order) and the functions to use it. Every section type (with its `contentVersion`, saved with its content; bump it when the content's fields change and add the upgrade step in `section.upgrade.ts`) and layout (name, description, async component, supported `backgrounds`, `options`, `layoutPhotoCount`, default content), plus `createDefaultSection(type)` and `changeSectionLayout(section, key)` (keeps the section's other fields, e.g. the editor's `key`; an option the host changed from the old layout's default carries over when the new layout has it and offers the value, e.g. Titles: Left from Simple list to Cards; the rest take the new layout's defaults, like the background) and `withLayoutOptionsOnly` (saving keeps only the options the layout has, as they are, so removed options don't linger)
   - `features/sections/section.photos.ts`: read and set a section's photos without knowing its type (`backgroundPhotoOf`, `withBackgroundPhoto`, `layoutPhotosOf`, `withLayoutPhoto` by slot). Every type has the same `backgroundPhoto` and (when its layouts have photos of their own) `layoutPhotos` fields, so it needs no per-type cases; a type without `layoutPhotos` (people, program) has none.
   - `features/sections/section.upgrade.ts`: `upgradeSectionContent(type, content, version)` brings content saved with an older `contentVersion` up to date, one step per version. Every type is at version 1 except `program` (2: `layoutPhotos` added, its step adds an empty list; 3: `venue` and `items` come from the event's program, its step drops them; 4: the venues block's text, its step adds `venuesHeading` "Getting there"), `hero` (2: `heading`, `date` and `venue` come from the event; its step drops them) and `countdown` (2: `heading` comes from the event; its step drops it). Saved content is upgraded where it enters the app: `websiteFromApi` (editor) and `EventSitePage` (published sites, which aren't re-saved).
   - `features/sections/section.links.ts`: `safeHref(href)`. Section content is what hosts saved, so every link a section renders goes through it: only `#…`, `http(s):`, `mailto:` and `tel:` become links, anything else (e.g. `javascript:`) renders without an `href`.
   - `components/sections/<type>/<Type><Layout>.vue`: one component per layout (e.g. `hero/HeroOverlayCard.vue`)
   - `components/sections/SectionRenderer.vue`: renders a `Section` through the registry, resolving its options (defaults filled in) and passing the page's `occasion` (a sample one when none is given)
   - `components/sections/SectionPhoto.vue`: a photo, or a soft placeholder in the event's colours when it's missing, so the layout keeps its shape (shared by every section type)
   - `components/sections/SectionPhotoCarousel.vue`: one photo spot that becomes a slideshow with several photos (crossfade every 5 s, dots to pick one; autoplay starts on mount, pauses on hover or focus, and stays off for `prefers-reduced-motion`); with one photo or none it renders like `SectionPhoto`. Such a layout's `layoutPhotoCount` is the most it plays
   - `components/sections/SiteThemeScope.vue`: applies an event's `SiteTheme` (`--site-*` variables on a `.crephore-site` wrapper) and plays its intro animation (features/site-motion) on load (`intro-on-load`, the public site, with `intro-content` from `introContentFor` for the scenes) or each time `intro-key` changes (the editor's and playground's "Play intro", inside the preview); `still` turns it off (thumbnails)
   - `components/sections/SectionThumbnail.vue`: a section rendered at desktop width and scaled into its box, for pickers (layouts, section types); not interactive
2. Layout components only take `SectionLayoutProps<T>` (`content`, `background`, `options`, `occasion`). No API calls, stores or route access, so the same component works everywhere, including server rendering.
   - `occasion` is the page's event (`name`, `venue`: its main venue's name, `startsAt` as a UTC instant, `timezone`, `program`: `SectionProgram`, the program's `venue`, `items` and `venues` (their details); a memorial's `bornOn` / `diedOn`, `"1938-05-01"`, when known). Details that belong to the event come from it and are never stored in section content, so they follow the event when it changes: the hero's heading (`name`), a memorial's life dates (`bornOn`, `diedOn`), date (`formatOccasionDate`) and place (`venue`), the countdown's heading (`name`) and target, and the program's venue and items. Pages pass it to `SectionRenderer` (`eventOccasion(event, program)` in the editor; the published site builds it from `SiteDto`'s `eventName`, `venueName`, `bornOn`, `diedOn`, `startsAt`, `timezone`, `program` and `venues`); previews without an event get `sampleOccasion()` ("Bea & Carlo" at Manila Cathedral, 112 days away, with the sample program on its day, and life dates 1938 – 2026, which only heroes set to show them and the memorial intros show). The date helpers take only `OccasionTime`.

Never use the Crephore app theme (`bg-primary`, `text-foreground`, …) inside a section; those are Crephore's colours, not the host's. The one exception is the white print border of photo frames (polaroids, framed mats), which is part of the look, not a colour.
   - Hosts can pick any colours, so never use the raw `--site-primary` or `--site-secondary` as text. Use the contrast-checked versions: `--site-primary-text` and `--site-secondary-text` (on light backgrounds), `--site-secondary-on-primary`, `--site-primary-on-secondary`, `--site-secondary-on-photo`, and the `--site-on-*` text colours. New brand-coloured text needs a checked variable in `siteThemeVars` (via `ensureContrast`) and a case in `test/nuxt/site-theme/useSiteTheme.test.ts`.
   - Buttons use the theme's accent on every background, or without one the other brand colour: primary on `light` and `secondary`; secondary on `primary` and `photo`. Never assume which colour is dark. Use `backgroundStyles[background].button` (`--site-button-<background>` / `--site-on-button-<background>`), which `siteThemeVars` adjusts to stand out (3:1) with readable text.
4. Each layout lists the backgrounds it supports (`backgrounds`, first = default): every layout offers all four (Light, Primary, Secondary and Photo, the optional background photo), never only one: a layout's name never assumes a photo. The hero's `fullscreen` ("Full") and `overlay-card` ("Floating card") and the countdown's `photo` ("Full") start on the photo; the others start on a colour (mostly `light`, the strip on `primary`, paper layouts on `secondary`) with `photo` last. The picker only offers those, always in the order Light, Primary, Secondary, Photo (`inPickerOrder`), whatever the layout's default, and `changeSectionLayout` moves a background that is still the old layout's default to the new layout's default (so switching from Full to Split goes from the photo to light), and keeps one the host picked. Layouts with their own photos never start on `photo`. Without a photo, the photo background renders exactly like `primary` (`SectionFrame` via `resolveBackground`). Background keys are stored on saved sections, so never rename one; display names live in `sectionBackgroundLabels`.
   - Responsive styles use container queries (`@sm:` … `@2xl:`, sized against `SiteThemeScope`, which is the `@container`), never viewport breakpoints (`sm:`, `md:` …), and don't name things `sm`/`md`/`lg`/`xl` either (the check reads `xl:` in an object key as a breakpoint). Sections then fit any frame: the full page, the playground's device preview, editor previews and thumbnails. `test/nuxt/sections/responsive.test.ts` enforces this. Use `@2xl:` (42rem) where you would otherwise use `sm:`, and `@3xl:` for the switch from stacked (phone) to side by side.
5. Pages render sections with `SectionRenderer` inside `SiteThemeScope`; never import layout components directly. Never set `--site-*` variables on `:root`.

Each section type has its own content controls there (`Playground<Type>Content.vue`; the program's edits the page's program, its items spread over one to three days from the occasion's date, which `PlaygroundSectionControls` passes on as `v-model:program`).
   - One component per layout, named after its key (`overlay-card` → `hero/HeroOverlayCard.vue`). Never let one component serve several layouts. Shared pieces that are not layouts live next to them so layouts stay consistent: `hero/HeroText.vue` (eyebrow, heading, date · venue, RSVP; slots `#before-heading`, `#after-heading`, `#before-cta` let a layout place photos in the flow; `labelledDetails` puts the button first and the date and venue under it as "Date" / "Location" columns); for every type, `SectionPhoto.vue` and `SectionPhotoCarousel.vue`.

Text there is always light: headings and names in the secondary (`--site-secondary-on-photo`) keep it as picked when it reads on the overlay (3:1 against its dark) and stands apart from that brightest spot (3:1, or clearly a different colour like buttons), else it's lightened (`lightenUntil`), never darkened. Elements with their own surface (the calendar page, the overlay card) keep their own colours.

## Event Program
The event's schedule belongs to the event (the API's `event_program_items`), not to a website section: every program section of its website shows it, and guests see changes without publishing again. Each item happens at one of the event's venues (see "Event Venues") or none.

1. Data: `features/event-programs/`.
   - `event-program.type.ts`: `EventProgram` (`items`: `EventProgramItem` with `id`, `date` `"2027-02-14"`, `startTime` / `endTime` `"15:00"` or null, `title`, `description`, `venueId` (one of the event's venues, or null), `speakers`), `UpdateEventProgramRequest`, and the Program tab's `EventProgramDraft` (items are section `ProgramItem`s keyed by `id`, plus their `savedId` and `venueId`).
   - `event-program.api.ts`: `getEventProgram`, `updateEventProgram` (`GET` / `PUT /events/{id}/program`; saving replaces the whole program, saved items by id).
   - `event-program.ts`: `programFromApi`, `mapProgramToRequest` (text trimmed, blanks as null), `isSameProgram`, `sectionProgram(program, venues)` (what sections show, with the venues' names: when every item is at the same venue it's the program's `venue` and the items show none, otherwise each item shows its own), `programErrors` (the API's item rules and messages, keyed like its errors, `items[2].title`) and `programItemLimits`.
2. The event page loads the program and venues with the event and owns them: the Program tab edits and saves the program (`@saved` updates the page), and the Website tab gets `sectionProgram(program, venues)` for the editor's occasion. When a saved change removes venues, the page reads the program again (the API moved their items to the main venue).
3. `EventProgramTab.vue`: the items in the order guests see them (up to `programMaxItems`, 40): drag or Arrow Up/Down on a handle to reorder; per item the title, a day (a shadcn `Select` of `programDayChoices`: the event's first to last day plus the day after, and the item's own date when it's another, e.g. the event moved), start and end times, venue (a shadcn `Select` of the saved venues, the first marked "Main venue", then "No venue" and "Add a venue…", which opens `EventAddVenueDialog`: every venue field, saved to the venues right away after the saved ones and picked for the item; `venues-saved` updates the page), speakers and note. A new item starts at the main venue; an item whose venue was removed moves to the main venue, as the API moves saved ones. Saving checks `programErrors` first and shows each error beside its item, as it does the API's. Save and Discard, and asking before leaving with unsaved changes, work like the Details form. Read-only without Owner access.
4. Tests: `test/nuxt/event-programs/` (the mappers and checks, the API), `test/nuxt/events/EventProgramTab.test.ts`.

## Event Venues
Where an event happens: a list per event (the API's `event_venues`), up to 10, in the host's order; the first is the **main venue**, whose name the dashboard, the hero and the intros show (`Event.venueName` and `SiteDto.venueName` are its name, "" without one). The event itself has no venue fields (the Details form has none); program items pick a venue by id.

1. Data: `features/event-venues/`.
   - `event-venue.type.ts`: `EventVenue` (`id`, `name`, optional `address`, `googleMapsUrl`, `appleMapsUrl`, `latitude` / `longitude`, `photoUrl`, `notes`: directions, parking and the like), `UpdateEventVenuesRequest`, and the editor's `EventVenueDraft` (text as strings, keyed, plus `savedId`).
   - `event-venue.api.ts`: `getEventVenues`, `updateEventVenues` (`GET` / `PUT /events/{id}/venues`; saving replaces the list, saved venues by id; a removed venue's program items move to the new main venue).
   - `event-venue.ts`: `blankVenue`, `venueFromApi`, `mapVenuesToRequest` (trimmed, blanks as null), `isSameVenues`, `venueErrors` (the API's rules and messages, keyed `venues[1].name`), `isGoogleMapsUrl` / `isAppleMapsUrl` (https on Google's or Apple's map hosts), `pinLinkOf` (Google Maps' link first, else Apple Maps'), `mapPreviewUrl` (Google Maps' keyless embed at the pin, `google.com/maps/embed`, whichever link the pin came from: Apple Maps refuses to be framed, and its embeddable map, MapKit JS, needs an Apple Developer token), `eventVenuesMax`, `venueLimits`. The website shows a program's venues inside its program sections (`sectionProgram`, see "Event Program"); there's no separate venue section (an earlier "Venue & map" section was removed; the published site skips section types it no longer has).
2. Map pins: hosts never place a pin. They paste the place's Google Maps and/or Apple Maps link; `server/api/map-pin.get.ts` (`GET /api/map-pin?url=…`, this app's own Nitro route, cached a day per link; `map-pin.api.ts` `getMapPin` calls it with `$fetch`, not the Crephore API) reads the pin out of the link, following short links' redirects one hop at a time and checking each hop (`server/utils/map-pin.ts`: `isMapLink` only opens https links on Google's and Apple's map hosts, every hop too; `parseMapPin`; `resolveMapPin`, sending Safari's user agent to Apple, whose short links only redirect for it, and a non-browser one to Google, whose short links answer browsers with a page that redirects by script; a page that answers instead of redirecting is read for a pin or its redirect, `readMapPage`; each hop logged in development). The pin is saved with the venue (`latitude`, `longitude`) for the preview and the website's map layouts; clearing the links clears it, and a link without a readable place says so.
3. `EventVenuesTab.vue` (the event page's Venues tab, between Details and Program): a card per venue (name, "Main venue" badge on the first, address, "Used by" its saved program items' titles), opened to edit with `EventVenueFields.vue` (shared with the add-venue dialog: name, address, Google Maps and Apple Maps links with where to copy them, the map preview beside the photo (`WebsitePhotoField` `large`: a box the map's height, with a white Replace and a red remove button over its top corner), then "Notes (optional)" for directions, parking and the like), "Make main venue" (moves it first) and "Remove venue" (confirmed when items use it, saying where they move). "Add a venue" adds one opened. Venues added from the Program tab join the list without losing edits here. Save, Discard and asking before leaving work like the Details form; errors show beside the field and open the venue. Read-only without Owner access.
4. Tests: `test/nuxt/event-venues/` (helpers, API, map-pin parsing and redirects), `test/nuxt/events/EventVenuesTab.test.ts`.

## Website Editor
Hosts build their event's website in the event page's Website tab (`dashboard/events/[id]/_components/`).

1. Flow: `EventWebsiteTab.vue` loads the saved website (skeleton while loading, "Try again" if it fails). With one, it opens `website/WebsiteEditor.vue`; without one, `EventWebsiteStart.vue` offers "Start from a template" or "Start from scratch". Scratch opens the editor on an empty page; the template picker is a placeholder for now. "Start over" (confirmed when the page has sections or is saved) deletes the saved website (`DELETE`) and goes back to the choice.
2. Data: `features/event-websites/`.
   - `event-website.type.ts`: `EventWebsiteDraft` (`theme` + `sections` in page order) and `WebsiteSection` (a `Section` plus the editor's `key`, the saved `id` once saved, `isVisible`, and `visibility`: `Always` / `BeforeEvent` / `AfterEvent`, always `Always` for now, with no editor control yet; kept as loaded so saving doesn't reset it); `EventWebsite` / `UpdateEventWebsiteRequest` for the API.
   - `event-website.api.ts`: `getEventWebsite` (`data` null when none is saved), `updateEventWebsite` (saves the whole website), `deleteEventWebsite`.
   - `event-website.ts`: `createBlankWebsite`, `defaultWebsiteTheme`, `eventOccasion(event, program)`, `withSampleProgram(occasion)` (the sample program with its venues), `createWebsiteSection(type, event)` (the type's default content plus `eventDetails`; never the event's name, date, venue or program, which sections read from the occasion), `duplicateWebsiteSection` (a new, unsaved copy), `moveItem`; for saving `websiteFromApi`, `mapWebsiteToRequest`, `isSameWebsite` (compares what would be saved) and `withSavedIds` (gives sections their ids after a save, by key, so edits made while saving stay).
   - Publishing: guests only see a published website, as it was when last published (see the backend's "Event Websites and Media"). The save bar shows "Not published", "Live" or "Live · changes not published" (`hasUnpublishedChanges` from the API, or unsaved edits). "Publish" / "Publish changes" saves unsaved changes first, then publishes (`publishEventWebsite`); it needs a visible section. "View website" opens the real address (`urlOf`) in a new tab once published. The "More" menu has Unpublish (confirmed) and Start over (which also takes a published website offline).
   - Saving works like the Details form: the editor edits a copy; the save bar (above the editor) shows "Not saved yet" / "You have unsaved changes" / "All changes saved", with "Save changes" and "Discard changes" (back to the saved website). A blank page that was never saved has nothing to save. Leaving the page with unsaved changes asks first (`onBeforeRouteLeave` + `beforeunload`).
   - Edits always replace objects (`{ ...section, … }`), never change them in place: the saved copy shares objects with the draft until they change.
   - Unused photos are dropped when saving, never while editing (`withoutUnusedPhotos` in `section.photos.ts`, applied by `mapWebsiteToRequest`): the background photo unless the background is Photo, and layout photos past the layout's `layoutPhotoCount`. The draft keeps them, so switching back to the photo background or a roomier layout during the session shows them again without a new upload; once saved (and so published), they're gone. Photos of items (about chapters, people) are content and always kept. `isSameWebsite` compares what would be saved, so adding or keeping an unused photo isn't an unsaved change.
   - One hero per page: every website has exactly one hero section, shown or hidden (`websiteProblem`, the same rule and messages as the API). Without one, or with several, the save bar shows why and Save and Publish are disabled (the Website tab's `save()` checks it too). The add dialog doesn't offer a second hero and the hero can't be duplicated; deleting it is allowed, and then the page needs a new one before saving.
3. Editor layout: a panel with Sections and Style tabs, next to a live preview (`PreviewFrame` + `WebsitePreview`) in the event's theme with the event as the occasion.
   - Sections: `WebsiteSectionList` (drag or Arrow Up/Down on the handle to reorder, eye to hide, menu to move, duplicate or delete with confirmation). "Add a section" (`WebsiteAddSectionDialog`) inserts after the section being edited, else at the end, then opens its settings with the layout picker already open (its first layout picked; closing keeps it). Clicking a section in the list or the preview opens `WebsiteSectionSettings`.
   - Section text inputs are shared (`website/`): `WebsiteTextField` and `WebsiteTextareaField` (a label and an input or textarea; `size="sm"` inside a list item; `required` marks it "Required" while empty) and `WebsiteListField` (a list of items, e.g. about's chapters and the people: a heading with the count, each item with a drag handle (drag, or Arrow Up/Down on it) and a remove button, "Add …" up to `max`; each item's fields in its `#item` slot; `name` names the items' `data-<name>-item` / `data-<name>-handle` hooks; `keyOf` keys items by id when they have one, else by position; `required` marks it "Required" while it has no items). Each type's `Website<Type>Fields.vue` builds its fields from them and keeps its own rule for an emptied field (removed, or kept as "").
   - Section settings, top to bottom: layout (thumbnail; "Change layout" opens `WebsiteLayoutPickerDialog`, thumbnails of every layout with the section's own content), placement options (`WebsitePositionPicker` for 3×3 positions, `WebsiteChoiceGroup` cards otherwise), background (`WebsiteBackgroundPicker`: `WebsiteChoiceGroup` cards with swatches in the event's colours; the background photo field only on Photo), one photo field per `layoutPhotoCount`, and the text (`Website<Type>Fields.vue`).
   - Text that comes from the event (the hero's heading, a memorial's life dates, date and place, the countdown's heading) is shown in `WebsiteEventFields.vue`: an info `CAlert` (`role="note"`, not an error) saying which fields are from the event details ("Heading, date and place are from the event details.") with an "Edit details" link to the Details tab, then each field's label and its value as plain text, indented (no input). Never add an editable field for it, and never store it in section content.
   - Picking one of a few choices uses `WebsiteChoiceGroup`: separate cards, the chosen one with a primary border, bold label and a check badge (not the joined outline toggle group), so the choice stands out.
   - Photos (`WebsitePhotoField`): "Upload photo" sends the file to `POST /events/{id}/media` (`features/media/media.api.ts`, `uploadPhoto`) right away and stores the returned URL in the section's content; the section itself is saved with the website. JPG, PNG, WebP or GIF up to 10 MB, checked in the browser first (`photoContentTypes`, `photoMaxBytes`) and again by the API.
   - Style: the shared `ThemeControls` (with the intro animation). "Play intro" plays it in the preview (`introKey`). The playground has the same controls, and a "Play intro" button above its preview too.
4. Hidden sections stay in the editor, faded in the preview, and are not shown to guests. Links inside sections don't navigate in the preview.
5. Editor chrome on the preview (selection outline, section labels) uses a fixed editor blue (`sky-500`), never the app's or the site's colours, so it can't be mistaken for part of a section on any background. The sections inside keep the site theme.
